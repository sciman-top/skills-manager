# AI 编码效能通用指南（跨项目参考件）

**定位**：面向"各种项目的日常 AI 编码"的通用参考，不是规则、不是门禁，不以全文进入任何宿主上下文。每条实践都标注来源与核实日期；与宿主官方文档冲突时以官方文档为准。本仓绑定自身机制的映射另见 [`ai-coding-playbook.md`](./ai-coding-playbook.md)。

**适用面**：Claude Code、Codex / ChatGPT、Cursor、Gemini CLI、ZCode/GLM、Antigravity、WorkBuddy 等主流编码代理，以及任何遵守 `AGENTS.md` 开放规范的工具。

---

## 0. 一句话结论

把 AI 当成**一个可以持续配置和改进的队友**，而不是一次性助手；把**上下文当成有限且会衰减的预算**，而不是可以无限灌入的容器。做到这两点，日常编码的产出、返工和维护成本会同时下降。

> "找到最小的、高信号的 token 集合，以最大化达成期望结果的概率。" —— Anthropic《Effective context engineering for AI agents》，2026-10-04 复核

---

## 1. 核心心智模型：三个必须先建立的认知

### 1.1 上下文是有限资源，且会"腐化"

- 模型准确回忆信息的能力**随上下文 token 数增加而下降**（context rot），这是所有模型共有的特性；LLM 每引入一个新 token 都要消耗一部分"注意力预算"。
- Transformer 的注意力是 n² 的成对关系，上下文越长，成对关系的捕捉越被稀释——**上下文规模与注意力聚焦天然对立**。
- 结论：上下文不是"给得越多越好"，而是**边际收益递减**。策展比堆砌重要。

**日常动作**：无关任务之间重置上下文（Claude Code `/clear`）；用 `/context` 确认文件是否真的加载；长任务主动压缩（`/compact <指令>`）。

### 1.2 持久指令要分层，且越短越有效

| 层 | 载体 | 作用 |
| --- | --- | --- |
| 个人/全局 | `~/.codex`、Cursor User Rules、用户级 `AGENTS.md` | 跨项目偏好（沟通风格、通用约定） |
| 仓库级 | 仓库根 `AGENTS.md` / `.cursor/rules` / `CLAUDE.md` | 该仓库的构建/测试/约定/禁区 |
| 子目录级 | 嵌套 `AGENTS.md` | 就近优先，子项目/包各自的细则 |

- `AGENTS.md` 是**面向代理的 README**（已有 6 万+ 开源项目采用），与 README 分工：README 给人看，AGENTS.md 给代理看。
- **就近优先**：离当前目录更近的文件优先。大型 monorepo 用嵌套文件（OpenAI 主仓有 88 个 `AGENTS.md`）。
- Cursor 侧同理：Project Rules（`.cursor/rules/*.mdc`，可按 `globs` 精确挂载）→ User Rules → Team Rules，越靠前优先级越高。

### 1.3 没有验证闭环，你本人就是验证循环

没有可运行的检查时，"看起来完成了"是唯一信号，于是你只能一遍遍肉眼复核——**成本高、且漏检**。给 AI 一个能自己跑出 pass/fail 的检查，闭环就自动闭合。

## 2. 六个杠杆：最大化发挥 AI 能力

### 杠杆 1｜上下文工程：给"最小高信号集合"

- **即时检索优于全量预载**：让代理维护轻量标识符（文件路径、查询、链接），运行时按需加载，而不是把整个仓库灌进去。类比人类：我们靠文件系统、书签按需检索，而不是背下全部资料。
- **渐进式披露**：文件层级、命名、时间戳都是信号（`tests/test_utils.py` 与 `src/core/logic/test_utils.py` 用途不同）。让代理逐层探索，只在"工作记忆"里保留必要内容。
- **混合策略**：稳定内容可预载（如 `AGENTS.md`），动态内容靠 `glob`/`grep`/`head`/`tail` 即时导航。Claude Code 就是这个模式。
- **长时程三技术**（按任务特性选）：
  - **压缩（compaction）**：接近上限时总结历史、重开窗口。保留架构决策、未解 bug、实现细节；丢弃冗余工具输出。先最大化召回，再提升精度；最安全的起点是"清除历史深处的工具调用与结果"。
  - **结构化笔记**：把持久事实写到窗口之外（`NOTES.md`、待办列表、记忆工具），需要时拉回。适合有里程碑的迭代开发。
  - **子代理（sub-agent）**：用干净上下文处理聚焦子任务，**只回传 1000–2000 token 的精炼摘要**。适合可并行、探索量大的工作。
- **反模式**：全仓灌入上下文、照搬其他仓的目录约定、无边界的"调查一下"。

子代理与并行代理须有用户或适用项目/技能规则的明确授权，并具有互斥写集和独立验收。本指南中的场景建议不授予委派、跨仓访问或宿主配置修改权限。

### 杠杆 2｜任务定义：四要素 + 冻结边界

一条好的默认提示词包含四要素（Codex 官方）：

| 要素 | 含义 |
| --- | --- |
| **Goal** | 要改变或构建什么（用户可见的结果） |
| **Context** | 相关文件/目录/文档/示例/错误（用 `@` 精确引用） |
| **Constraints** | 必须遵循的标准、架构、安全要求、不得触碰的目录 |
| **Done when** | 完成标准：测试通过、行为改变、bug 不再复现 |

在此基础上，对"有风险或易蔓延"的任务再加两条边界：**Exact write set（精确写集）** 与 **Stop（停止条件）**——达到即停，不顺手重构、不吸收无关优化。

**具体提示技巧**（Claude Code 官方，Before → After）：

- **限定范围**："给 foo.py 加测试" → "为 foo.py 写测试，覆盖用户登出时的边界情况，避免 mock"
- **指向来源**："为什么 ExecutionFactory 的 API 这么怪？" → "查 ExecutionFactory 的 git 历史，总结其 API 由来"
- **引用现有模式**：指定仓库内某个文件为范例，"遵循该模式，不引入库外依赖"
- **描述症状**：症状 + 可能位置 + "修好"的定义（"登录在会话超时后失败，检查 src/auth/ 的令牌刷新，先写复现测试再修"）

> 注：**模糊提示在探索阶段是有用的**（"这个文件你会怎么改进？"）。四要素是给"要动手"的任务用的，不是所有对话的模板。

### 杠杆 3｜工作流阶段：探索 → 计划 → 实现 → 验证 → 提交

- **探索**：只读，不改动（Claude Code `plan mode`、Codex `/plan`）。
- **计划**：对**复杂、模糊、多文件、不熟悉**的任务先出计划；Codex 还提供"让 AI 访谈你"——用提问把模糊想法变具体。
- **实现**：退出计划模式后编码，**同时写/更新测试并运行**。
- **验证**：见杠杆 5。
- **提交**：让代理用描述性信息提交/开 PR，并跑完仓库礼仪要求的检查。

**何时跳过计划**：范围明确、改动小（改错字、加日志、重命名）。判据很实用——**如果你能用一句话描述这个 diff，就跳过计划**。

### 杠杆 4｜持久指令的"减法"：删掉会致错吗

这是最高杠杆、也最常被做错的一环。**臃肿的指令文件会导致 AI 忽略你的实际指令**——规则越多，每条越不突出。

**应写进 `AGENTS.md` / rules 的**：

- AI 猜不到的构建/测试/运行命令与首选运行器
- 与默认不同的代码风格、项目特有的架构决策
- 仓库礼仪（分支命名、PR 格式、提交约定）
- 开发环境怪癖（必需的环境变量、本地服务的启动顺序）
- 反复踩到的坑与非显然行为
- "完成"的定义与如何验证

**不应写的**：读代码就能知道的、标准语言惯例、详细 API 文档（给链接）、频繁变化的信息、长篇教程、逐文件描述、"写干净代码"这类自明实践。

**逐行自问**："删掉这行，会导致 AI 犯错吗？" 不会就删。

**Cursor 官方补充**：规则保持 500 行以内；拆成可组合的多条；给具体示例或引用文件；避免含糊指导；**指向规范示例而不是复制代码**（复制会随代码变化而失效）。**不要**复制整份风格指南（用 linter）、不要枚举通用命令、不要为罕见边缘情况写规则。

**规则演进的依据**：真实失败、反复出现的人工成本或必要外部契约。重复错误先定位规则是否加载、实际入口是否覆盖、裁决是否可执行；能由现有脚本或权限层解决时修正该入口。安全或数据问题无需等到第二次发生，也不应每次失败都追加提示语。

### 杠杆 5｜验证闭环：只认证据，不认声明

- **核心**：给代理一个能产生 pass/fail 的检查——测试套件、构建退出码、linter、对比 fixture 的脚本、对比设计的浏览器截图。
- **要求展示证据而非断言成功**：测试输出、所运行的命令及其返回、结果截图。代理自检通过后，重要改动再自己跑一次 `/verify` 或人工确认。
- **验证方式与边界**（按当前风险选择，不是每次必经的流水线）：

| 方式 | 做法 | 适用与边界 |
| --- | --- | --- |
| 任务内验证 | 要求运行受影响检查并给出命令、退出码和结果 | 日常小改；提示语本身不强制执行 |
| 持续目标 | 在支持的宿主中保存目标与验收条件，例如 `/goal` | 保持目标连续；不把目标记录或模型评估当成硬权限 |
| Stop hook | 在宿主支持、已加载且可信的停止事件中检查必要证据 | 只覆盖该事件；不能撤销已发生的写入，不能声称零例外保证 |
| 独立复核 | 有风险依据且获授权时，用新上下文寻找具体反例 | 第二意见补充证据，不能替代行为测试 |
| CI 与远端必需检查 | 将现有检查绑定到受保护分支的合并规则 | 阻止未满足检查的集成；单有 workflow 不代表已强制，仍须核对 bypass 与检查来源 |

Hook 必须按当前宿主的事件、工具覆盖、信任和错误语义验收。以 Codex 为例，`Stop` 的 block 会触发续做，`PreToolUse` 才用于受支持工具的事前阻断；MCP hook 的连接或工具错误不会自动阻断操作。不能把“脚本失败”直接解释为“动作被拒绝”。详见第 8 节。

- **坏例 → 好例**：
  - "构建失败了" → "构建以此错误失败：[粘贴错误]。修复并验证构建成功，解决根因，不要屏蔽错误"
  - "实现一个验证邮箱的函数" → "写 validateEmail，用例：`user@example.com` 为 true，`invalid` 为 false，`user@.com` 为 false；实现后运行测试"

### 杠杆 6｜沉淀：把重复工作变成资产

- **重复即技能**：如果你反复使用同一提示词、或反复纠正同一工作流，它就该成为一个 Skill（`SKILL.md`）。
- **一个技能一个任务**；从 2–3 个具体用例起步，定义清晰输入输出；描述里写清"做什么 + 何时用"，并包含用户实际会说的**触发短语**。不要一开始就覆盖所有边缘情况。
- **技能定义方法，计划任务定义时间表**：工作流仍需大量引导时先做成技能；**手工运行稳定后**再调度。不要在还没跑稳时就定时化。
- **三层沉淀**：契约/约定 → `AGENTS.md`；可复用方法 → Skill；已手工跑稳的流程 → 计划任务/CI。

## 3. 常见问题 → 防法（按类别）

### 3.1 上下文类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **厨房水槽会话** | 一个任务里塞进无关任务，上下文被无关信息填满 | 无关任务之间 `/clear`；一个连贯成果一个对话，不要整个项目一个对话 |
| **无限探索** | 无范围地"调查"，读了数百文件 | 严格限定调查范围；探索用 subagent 隔离，只回传摘要 |
| **长会话退化** | 反复犯错、忘记早先约束 | 主动 `/compact` 或重开；把稳定事实写进 `NOTES.md`/记忆工具 |
| **上下文腐化** | 上下文越满，准确率越低 | 视为有限预算；即时检索替代全量预载 |

### 3.2 指令/规则类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **规则膨胀反噬** | 规则文件很长，AI 却"看不见"关键几条 | 逐行过"删掉会致错吗"；只保留非显然、猜不到的内容 |
| **规则与实现脱节** | 文档声称覆盖，实现其实没有 | 规则/文档不复制运行状态；改动后同步更新；用测试或校验脚本钉住 |
| **规则写进提示词** | 每次对话重复粘贴同一约定 | 移到 `AGENTS.md` / 规则 / Skill，一次配置、长期生效 |
| **只跳一条指令** | 某条规则总被忽略 | 单独给该行加"IMPORTANT"；**多行都强调 = 一行都不突出** |
| **AI 反复问已答的问题** | 明明写了还问 | 说明措辞有歧义，改写该条 |

### 3.3 任务/目标类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **范围蔓延 / 过度设计** | 顺带重构、加"以后可能有用"的抽象 | 冻结 Goal / 写集 / Stop；审查时要求 "Report gaps, not style preferences" |
| **跳过规划** | 多步复杂任务直接动手，方向跑偏 | 复杂/多文件/不熟代码先出计划；一句话能描述 diff 才跳过 |
| **目标错位 / 自证正确** | 做对了"自己以为的需求" | 用**具体用户操作**定义验收；重要改动独立复核需求、diff、反例 |
| **把输入/工具故障误判为模型不足** | 一失败就换模型/改配置 | 分别检查输入、工具执行、认证、额度、端点、协议；证据不足时不改模型配置 |

### 3.4 验证类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **信任-验证缺口** | 实现看似合理，边界未处理 | 始终提供验证（测试/脚本/截图）；**无法验证就不发布** |
| **汇报与实态不符** | 声称成功但没证据 | 命令/界面/请求链证据必须直接支持结论；Git 状态只说明文件变更 |
| **测试迁就实现** | 改测试让代码"通过" | 不许改测试迁就实现；行为变化显式走契约迁移 |
| **假阳性/噪声** | 未部署环境下必然 FAIL 与真实风险混同 | 缺失配置记"未配置"而非"风险"；区分环境问题与真实缺陷 |

### 3.5 协作/权限/并行类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **权限过大** | 未理解工作流就给全权限 | **从最小权限起步**，仅在可信仓库或明确需要时放宽 |
| **并行互踩** | 多任务在同一批文件上互相覆盖 | 用 **git worktree** 隔离；同一批文件不要跑并行的实时任务 |
| **逐步微管理** | 盯着 AI 一步步走，效率反低 | 让单个主执行者自主完成闭环；只在写集互斥、可独立验证且净收益为正时并行 |
| **把配置问题当模型问题** | 工作目录错、缺写权限、模型默认值错 | 尽早为真实环境配置；很多"质量问题"其实是设置问题 |

### 3.6 审查类

| 问题 | 症状 | 防法 |
| --- | --- | --- |
| **审查诱发过度设计** | 被要求"找缺口"的审查者总能报出一堆 | 审查者**只标记影响正确性或既定需求的缺口**，其余视为可选 |
| **自评偏差** | 实现者给自己打分 | 用全新上下文审查 diff（Writer/Reviewer 模式） |
| **把"同意"当验证** | 第二个模型也说没问题就放心 | 第二个模型的同意**不构成验证**，它只是另一个信号 |

## 4. 失败升级：两次规则

- **两次纠正规则**：同一问题连续纠正失败两次，先保留目标、已证实事实、失败尝试和未决问题；按实际原因澄清、压缩或换上下文。换上下文不自动修复缺失输入、权限、认证或工具错误，也不能丢弃原授权和停止条件。
- **两次失败整理**：同一问题连续失败两次，先整理**已证实事实、失败尝试、未决问题**，再决定澄清还是换上下文；不要盲目连续打补丁。
- **失败反馈模板**：目标行为 / 实际行为（原始错误、去秘密）/ 复现条件 / 已尝试及各自证据。沿实际调用路径诊断，区分**输入缺失、工具/环境失败、代码错误**三类。

## 5. 分场景速查

| 场景 | 关键动作 |
| --- | --- |
| **新项目上手** | 先写 `AGENTS.md`（`/init` 生成后**必须编辑**）：构建/测试命令、约定、禁区、完成定义 |
| **大型/多包仓库** | 嵌套 `AGENTS.md`，就近优先；子项目各自带细则 |
| **模糊需求** | 先让 AI **访谈你**（提问、挑战假设），把想法变具体，再计划 |
| **大迁移/批量改** | 先 2–3 个文件试点精修提示，再 `/batch` 或循环 `-p` 扇出；每份在自己的 worktree |
| **高风险改动** | 计划 + 更强推理档位 + 独立审查（新上下文）+ 明确回滚 |
| **长期/多步任务** | 压缩 + 结构化笔记 + 子代理三件套；关键决策落盘 |
| **反复出现的流程** | 先做成 Skill，跑稳后再考虑定时任务 |
| **前端/交互** | 用开发服务器 + 截图 + 控制台证明；编译成功不能替代渲染验证 |
| **API/服务** | 请求标识 + 入口到外部效果的日志 + 实际 ACK；mock / HTTP 200 不等于真实交付 |

## 6. 一页速查卡

**给 AI 的（每次任务）**：Goal / Context / Constraints / Done-when（+ 写集 / Stop）
**给仓库的（一次配置）**：`AGENTS.md` 短而准，只写猜不到的；两次同错才加规则
**给上下文的（持续维护）**：无关任务 `/clear`；长了就 `/compact`；探索用 subagent
**给验证的（每次交付）**：一个能自己跑的 pass/fail 检查；要证据不要声明；改测试不算通过
**给权限的（逐步放开）**：最小权限起步；并行用 worktree；理解工作流再给全权限
**给沉淀的（重复即资产）**：重复提示 → Skill；跑稳流程 → 定时；两次同错 → 更新规则
**给失败处理的（两次规则）**：纠正两次 → 重开；失败两次 → 先整理事实再决定

## 8. 约束为何失效，怎样形成可执行裁决

“充分、高效、遵守范围”包含需要判断的目标，不能仅靠一段文本获得绝对保证。工程上能强制的是明确且可检测的禁止条件、权限边界和交付条件；其余判断通过相关上下文、行为验收和有依据的复核提高可靠性。

### 8.1 先沿实际执行路径定位根因

- **未加载或加载过期**：检查当前启动目录、有效规则源、技能正文及新会话加载事件。磁盘文件相等不能证明正在运行的宿主使用了它们。
- **语义没有可检测条件**：把用户目标写成具体输入、期望行为、写集和停止条件；不要用“质量更高”替代验收。
- **裁决没有覆盖实际入口**：核对 shell、补丁、MCP 和原生工具；命令前缀策略不是所有文件写入的通用沙箱。
- **故障被错误解释为阻断**：hook 未信任、被跳过、连接失败或返回不支持的字段时，动作可能继续；必须观察禁止动作是否真的未发生。
- **证据与目标不同**：测试通过、构建通过和投影完成分别证明各自层次，不能外推宿主加载、外部效果或自然用户验收。
- **验证失去比例**：没有独立风险却反复 full、审计或重试；已通过证据的输入没有变化时复用，只重跑失效部分。耗时须带执行环境，仪表化指纹不证明具体延迟成因。

### 8.2 将裁决放在对应动作发生的位置

| 层 | 承担的责任 | 必须保留的边界 |
| --- | --- | --- |
| 用户目标、`AGENTS.md`、Skill | 需求、仓库事实、方法、验收与 stop | 指导模型；不是不可绕过的访问控制 |
| 宿主 sandbox、permissions、managed policy | 文件、网络、命令和外部副作用的权限 | 按实际宿主配置；全权限不能提高业务正确性 |
| 命令 rules | 对覆盖的命令作允许、审批或拒绝裁决 | Codex `.rules` 控制沙箱外命令；精确前缀不能替代语义判断或文件沙箱 |
| 事前 hooks | 在覆盖且实际触发的工具事件中检查、拒绝 | 验证信任、覆盖和错误路径；事后 hook 不能撤销副作用 |
| 现有受控写入入口 | 检查精确目标、授权、before hash 和回滚；失配即拒绝 | 只有通过该入口的操作受其裁决；hash 复核不等于原子锁 |
| 现有 build、tests、contract 脚本 | 可重复的行为和契约检查，返回可靠退出码 | 测试选择以受影响行为为准；不能由自述补足缺失证据 |
| CI 与远端分支规则 | 对集成提交执行检查并强制所需结果 | 核对必需检查来源、允许绕过者及合并路径；不得自行改变远端权限 |
| 宿主与实际链路验收 | 观察加载、真实调用和预期效果 | 单独授权和报告；不是普通编码的无条件前置步骤 |

### 8.3 强制机制的最低验收

先选择一个真实反复失败的条件，并复用最接近该动作的已有入口。最低证明包括：合法动作可执行；禁止动作被阻断且没有副作用；输入漂移会被拒绝；依赖或 hook 故障时实际行为符合约定；新会话在目标宿主确实加载并触发该裁决。未完成宿主证明时只报告已验证的脚本或投影层次。

涉及不可接受副作用时，应由受控写入入口、OS/宿主权限或远端集成策略承担最终拒绝。模型可修改或跳过的脚本、自我声明的 receipt 和未验收的 hook 不足以提供这一保证。

效率裁决优先使用现有比例门禁、失败分类、超时和有效证据复用。Stop hook 若确有调用方，只检查当前最低证明，不在每次停顿重新运行 full；不为普通任务新增 admission JSON、报告系统、第二状态库或固定模型接力。
