# Agent 沙箱仪表化：指纹、实测影响与操作规则

**定位**：runbook。记录 agent 会话中进程被注入的沙箱仪表化（shim / 代理 / 守卫）的**可检测指纹**、**实测影响**与**必须遵守的操作规则**。目的是防止"把沙箱开销误读成代码成本"这一类问题反复出现。
**核实日期**：2026-10-04（本机 Windows / WorkBuddy 桌面版）。

---

## 1. 问题现象

同一份代码、同一份测试，**在 agent 工具里跑和在普通终端/CI 里跑，耗时可能差一个数量级**。历史实例：

- 本仓 full 门禁顺序运行记录为 **19303s（≈5.4h）**；该记录来自 2026-10-04 的 WorkBuddy Windows 桌面会话，不是 ZCode 会话的通用基线。
- 分片全量：agent 工具启动的分片 **1319.6s**（361 用例）vs 另一路启动的**同分片 124.9s**（同样 361 用例）——**10.6 倍**。
- 若把这组 WorkBuddy 记录外推到所有宿主，会得出"门禁太慢、需要砍测试"的错误结论。

---

## 2. 可检测指纹

### 2.1 环境变量（诊断线索，存在性不等于启用状态）

| 变量 | 含义 |
| --- | --- |
| `CODEBUDDY_SAFE_DELETE_ENABLED=1` | 安全删除 shim 已启用 |
| `CODEBUDDY_SAFE_DELETE_SANDBOX=1` | 运行在沙箱删除通道 |
| `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=50` | 单次删除超过该文件数即要求**宿主弹窗确认** |
| `CODEBUDDY_SAFE_DELETE_BULK_STATE_DIR` | 守卫状态目录 |
| `CODEBUDDY_SAFE_DELETE_BROKER_DELETE` | 删除 broker 脚本（**每次删除的 IPC 目标**） |
| `CODEBUDDY_SAFE_DELETE_BIN_DIR` | shim 的 `safe-bin`（Git Bash 的 `rm` 包装在此） |
| `CODEBUDDY_SAFE_DELETE_REPORT_PATH` | 删除审计 jsonl |
| `NODE_OPTIONS=--require=<...>/node-language-shim.cjs` | Node 进程经此注入 |
| `PYTHONPATH=<...>/cli/vendor/shim` | Python 进程经此注入（`sitecustomize`） |
| `HTTP_PROXY` / `https_proxy` = `http://127.0.0.1:<port>` | 遵循代理变量的客户端可能经本地代理；变量本身不证明代理归属或所有流量路径 |
| `SANDBOX_CENTER_IPC_ADDRESS` / `SANDBOX_CENTER_UID` | 沙箱控制面 IPC |

核对具体启用值、包装来源和实际调用行为；仅有变量名、普通代理配置或 `shim` 字样不足以证明守卫已介入。`tests/run.ps1` 的 `environment.json` 是诊断记录，不能单独证明某项开销来自沙箱，也不能替代宿主执行证据。

> ⚠️ 同一环境里还包含**长期凭据**（网关口令、GitHub token 等）。任何被 agent 启动的子进程都能读到它们 ⇒ **不要把完整 `env` 输出粘进聊天/日志/提交**；若已外泄，轮换凭据。

### 2.2 PowerShell 侧

```powershell
(Get-Command Remove-Item).CommandType
```

`Function` 表示命令存在包装，须进一步核对包装来源；不能仅凭命令类型认定它属于沙箱。

## 3. 实测：创建与删除样本的证据边界

本机 2026-10-04 实测：

| 操作 | 结果 |
| --- | --- |
| 纯创建 40 个小文件 × 5 轮 | **71–109 ms/轮**（≈400–560 files/s）；仅证明该创建样本完成 |
| 创建 40 文件 + `Remove-Item -Recurse -Force` | **第一轮即无输出，整个调用 exit 1**；具体失败原因须结合守卫日志确认 |

**本次可确认**：创建样本能完成，创建加删除样本失败；删除路径是需要追踪的边界。结合 shim 函数与 broker IPC 的观测，删除密集型测试可能受守卫影响，但尚不能把 full 门禁的全部延迟归因于删除，也不能由这两个样本推导所有读取、计算或 I/O 的开销。

**尚未定论**：`HTTP_PROXY` 对**联网测试**的额外延迟未实测。含网络调用的测试应单独怀疑。

### 3.1 ZCode 会话实测（2026-10-05，指纹面外）

ZCode 沙箱会话内（Bash 工具直跑 pwsh 子进程）：§2.1 全部环境变量为空、`(Get-Command Remove-Item).CommandType` 为 `Cmdlet`（未包装）、30 文件递归删除历史诊断样本 **0.01s**——当前指纹面内**无任何仪表化**，主工作树全量分片实测 211s（≈CI 水平）。该样本只作历史诊断记录，不是 full 门禁的前置测量。

- 小时级膨胀的实证（§1）来自**命中这些指纹的 WorkBuddy 系宿主会话**，不能外推到所有 AI 会话；无指纹会话的正常耗时也不证明其他宿主永远不会变慢。
- `run-local-quality-gates.ps1` 已按 §2 的 shim/environment 指纹（safe-delete 环境标记、sandbox IPC、Node/Python shim、`Remove-Item` Function 包装）阻断非 CI 的 `-Profile full`（`-AllowShimmedFull` 显式豁免）；普通代理、跨盘 Temp worktree 等未被证明属于同一原因的慢路径不在该阻断覆盖内，仍按 §4 报告条件与缺口。

### 3.2 WorkBuddy 沙箱内逐操作单价（2026-10-05 实测，指纹面内）

同一次会话内的进程内采样（探针见 `reports/agent-review/probe-sandbox-cost*.ps1`）。**结论：被代理的是「变更类」操作（删除条目、创建进程）；读取、枚举、哈希、脚本解析全部正常。**

| 操作 | 沙箱内实测 | 判别 |
| --- | --- | --- |
| `Remove-Item -Recurse` 10 / 50 / 200 / 1000 文件 | 0.72s / 1.84s / 6.04s / **27.99s**（≈28ms/文件，线性） | 按条目计费 |
| `Remove-Item -Recurse` **100 目录 × 3 文件** | **58.55s（≈0.5s/目录）** | 目录删除比文件删除贵 ~18× |
| 创建 200 文件 | 0.50s | 变更类，但远低于删除 |
| `git init + add + commit`（1 夹具仓） | **5.36s** | per-test git 夹具是重灾区 |
| 子进程创建（热态） | 0.99–1.19s | ~10× 原生 |
| 子进程创建（冷/争用） | **60.08s**（首个子进程） | 间歇、不可预测 |
| pwsh 进程创建 → 脚本第一行 | 1.84s（热）／**~228s**（冷，观测 1 次） | 0 字节日志的来源 |
| `Get-ChildItem -Recurse` 14585 文件 | 1.76s | **正常（1×）** |
| `ReadAllText` 1.6MB × 100 | 0.71s | **正常（1×）** |
| `Test-Path` × 500 / `Get-FileHash` 420KB | 0.13s / 0.00s | **正常（1×）** |
| `Get-Date` / 纯字符串字面量 | 0.06s / 0.00s | **正常（1×）** |

**间歇性（不可用单次耗时下结论）**：同一台机器、同一个文件，`tests/Unit/Log.Tests.ps1`（2 用例）本日先后为 **122.1s** 与 **7.7s**（13.6×）；同一 6 文件批（387 用例）在 16:36 为 **40.9s 全绿**。

**⚠️ 对 §3 表格的更正**：2026-10-04 记的「创建 40 文件 + 递归删除 → 第一轮即无输出、exit 1」**不是可复现的守卫行为**。2026-10-05 的 200 / 1000 文件与 100 目录样本**全部正常完成（exit 0）**，未被杀。守卫（阈值 50）作用于 Git Bash 的 `rm` / `safe-bin` 包装，**不作用于 PowerShell 的 `Remove-Item`**；那条记录的更可能解释是**工具调用超时或宿主侧瞬时停顿**，而非确定性的守卫终止。

### 3.3 优化杠杆实测：哪些有用、哪些没用（2026-10-05）

**结论：唯一有效杠杆是「减少外部进程启动次数」，不是减少文件/目录条目数。**

| 尝试 | 实测 | 判定 |
| --- | --- | --- |
| 换递归删除实现：`[IO.Directory]::Delete` / `DirectoryInfo.Delete` / `cmd /c rmdir /s /q` vs `Remove-Item -Recurse`（50 目录 × 3 文件） | 25.5 / 26.2 / 23.8 / 26.5 s | ❌ 无差异——删除成本在沙箱层，实现换不掉 |
| 扁平 300 文件目录的删除 | `cmd rmdir` 1.36s vs `Remove-Item` 8.13s | ⚠️ 单次样本，未复现，不作为依据 |
| `git init --template=`（空模板） | 条目 27→9，但耗时 0.40→0.32s；完整夹具（init+add+commit）4.27→4.40s | ❌ 无效——成本由**进程启动**主导 |
| **一次 `git init` 做模板 + 逐次复制 `.git`（26 条目）** | **0.36s → 0.05s / 仓（≈7×）**；复制出的仓库 `symbolic-ref=main`、`show-ref refs/heads/main` exit 1、`remote` 空、`status` 空，与新建完全等价 | ✅ **有效**（已用于 `tests/Unit/RuleEstate.Tests.ps1`） |
| 单次 `git init` 本身 | 0.36–0.40s | 每次调用都按"进程启动"计费 |

> 推论：**per-test 的 git / CLI 调用是主要成本项**。夹具应优先**复用**（复制现成产物）而不是反复调用外部命令；`RuleEstate` 夹具原先每用例跑 5 次 `git init`，改成复制后 35 个用例共减少 175 次进程启动。

## 4. 操作规则（防重现）

1. **耗时结论必须限定执行环境。**
   对"门禁要 5 小时 / 测试太慢"的判断，应保持源码、测试选择、并行度与依赖可比，并在已授权的用户终端或 CI 对照复核。CI 超时预算以 `.github/workflows/ci.yml` 为准；预算配置不是实际运行耗时或成功证明。
2. **按风险选择验证，再选择可完成该验证的执行位置。**
   agent 内默认沿 auto/focused 完成最低充分证明；仓库风险确需 full 时，仍须获得一次有效 full 结果。守卫阻断或执行环境不可用时，记录缺口并使用已授权的 CI/终端路径，不把抽样升级成 full 通过，不因环境受阻修改安全控制。
3. **报告耗时必须带条件。**
   写明"经 agent 工具启动 / 命中 shim 指纹"，否则读者会默认它是代码成本。
4. **测试与夹具避免大批量递归删除。**
   删除是**按条目计费**的沙箱开销（§3.2：≈28ms/文件、**≈0.5s/目录**），是本类"测试很慢"的主要来源；夹具优先建**少量文件**而不是**多层目录**，并避免 per-test 的 `git init` 夹具仓（≈5.36s/次）。
   Git Bash 的 `rm` / `safe-bin` 包装在批量删除时还会触发守卫（阈值 50）并要求**宿主弹窗确认**——agent **不能自我批准**。
   ⚠️ **不得**以"拆小批删除 / 删失败就静默放弃"来规避守卫——那属于绕过安全控制。
5. **不要从 agent 内关闭或绕过 shim / 代理。** 需要干净环境时，换执行位置，而不是改安全配置。
6. **不要把测试输出静默重定向到文件后干等。**
   完成前日志是 **0 字节**（§3.2），叠加间歇的进程创建停顿后，"仍在启动"与"已挂死"在观感上无法区分。用后台任务 + 事后读日志，并在判定挂死前先确认**进程是否还活着**与**是否有回执**（`reports/test-shards/**/targeted.receipt.json`）。
7. **夹具复用优先于反复调用外部命令。**
   每个 git / CLI 调用都按"进程启动"计费（§3.3：`git init` 0.36s/次 vs 复制现成 `.git` 0.05s/次，状态等价）。per-test 的 `git init` / `git config` / CLI 调用是测试变慢的主要可控项；能用一次准备 + 复制/复用替代的，就不要每次重跑。

## 5. 上报上游所需的复现材料

若要让**产品侧**彻底修复（而不是每次靠人识别），带上以下最小证据：

1. 指纹：`env` 中 `CODEBUDDY_SAFE_DELETE_*`、`NODE_OPTIONS`、`PYTHONPATH`、`HTTP_PROXY` 的**存在性**（值可脱敏）。
2. `(Get-Command Remove-Item).CommandType` 的输出。
3. 对比数据：**纯创建 N 文件耗时** vs **删除同批耗时** vs **删除 N 个目录耗时**（2026-10-05：创建 200 文件 0.50s；删除 200 文件 6.04s、1000 文件 27.99s；删除 100 目录 × 3 文件 58.55s）。
4. 期望的修复方向：删除 shim 应**按需介入**（仅在实际发生批量删除时走 broker），而不是每次删除都 IPC；目录删除与进程创建不应按节点/次计费；或提供**文档化的干净测量模式**。

---

## 6. 边界

- 本文是**本机 2026-10-04 / 2026-10-05 的实测**，指纹与阈值随客户端版本可能变化；复用前重新探测。
- 未测：`HTTP_PROXY` 对联网测试的量化影响；其他语言运行时（Go/Java）的注入方式。
- 本文不构成对任何宿主配置、shim 或代理的修改授权。
