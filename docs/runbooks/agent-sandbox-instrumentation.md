# Agent 沙箱仪表化：指纹、实测影响与操作规则

**定位**：runbook。记录 agent 会话中进程被注入的沙箱仪表化（shim / 代理 / 守卫）的**可检测指纹**、**实测影响**与**必须遵守的操作规则**。目的是防止"把沙箱开销误读成代码成本"这一类问题反复出现。
**核实日期**：2026-10-05（本机 Windows / WorkBuddy 桌面版；§3.3–3.5 为同日第二轮更严格对照，**修正了第一版的计费模型**）。

---

## 1. 问题现象

同一份代码、同一份测试，**在 agent 工具里跑和在普通终端/CI 里跑，耗时可能差一个数量级**。历史实例：

- 本仓 full 门禁顺序运行记录为 **19303s（≈5.4h）**；该记录来自 2026-10-04 的 WorkBuddy Windows 桌面会话，不是 ZCode 会话的通用基线。
- 分片全量：agent 工具启动的分片 **1319.6s**（361 用例）vs 另一路启动的**同分片 124.9s**（同样 361 用例）——**10.6 倍**。
- 若把这组 WorkBuddy 记录外推到所有宿主，会得出"门禁太慢、需要砍测试"的错误结论。

## 2. 可检测指纹

### 2.1 环境变量（诊断线索，存在性不等于启用状态）

| 变量 | 含义 |
| --- | --- |
| `CODEBUDDY_SAFE_DELETE_ENABLED=1` | 安全删除 shim 已启用 |
| `CODEBUDDY_SAFE_DELETE_SANDBOX=1` | 运行在沙箱删除通道 |
| `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=50` | 单次删除超过该文件数即要求**宿主弹窗确认** |
| `CODEBUDDY_SAFE_DELETE_BULK_STATE_DIR` | 守卫状态目录 |
| `CODEBUDDY_SAFE_DELETE_BROKER_DELETE` | 删除 broker 脚本（**每次删除的 IPC 目标**） |
| `CODEBUDDY_SAFE_DELETE_BIN_DIR` | shim 的 `safe-bin`（Git Bash 的 `rm` 包装在此） |
| `CODEBUDDY_SAFE_DELETE_REPORT_PATH` | 删除审计 jsonl |
| `NODE_OPTIONS=--require=<...>/node-language-shim.cjs` | Node 进程经此注入 |
| `PYTHONPATH=<...>/cli/vendor/shim` | Python 进程经此注入（`sitecustomize`） |
| `HTTP_PROXY` / `https_proxy` = `http://127.0.0.1:<port>` | 遵循代理变量的客户端可能经本地代理；变量本身不证明代理归属或所有流量路径 |
| `SANDBOX_CENTER_IPC_ADDRESS` / `SANDBOX_CENTER_UID` | 沙箱控制面 IPC |

核对具体启用值、包装来源和实际调用行为；仅有变量名、普通代理配置或 `shim` 字样不足以证明守卫已介入。`tests/run.ps1` 的 `environment.json` 是诊断记录（分片与定向运行均写入各自 run 目录；定向起跑行在命中指纹时追加 `instrumented_sandbox=yes` 后缀），不能单独证明某项开销来自沙箱，也不能替代宿主执行证据。

> ⚠️ 同一环境里还包含**长期凭据**（网关口令、GitHub token 等）。任何被 agent 启动的子进程都能读到它们 ⇒ **不要把完整 `env` 输出粘进聊天/日志/提交**；若已外泄，轮换凭据。

### 2.2 PowerShell 侧

```powershell
(Get-Command Remove-Item).CommandType
```

`Function` 表示命令存在包装，须进一步核对包装来源；不能仅凭命令类型认定它属于沙箱。

## 3. 实测：创建与删除样本的证据边界

本机 2026-10-04 实测：

| 操作 | 结果 |
| --- | --- |
| 纯创建 40 个小文件 × 5 轮 | **71–109 ms/轮**（≈400–560 files/s）；仅证明该创建样本完成 |
| 创建 40 文件 + `Remove-Item -Recurse -Force` | **第一轮即无输出，整个调用 exit 1**；具体失败原因须结合守卫日志确认 |

**本次可确认**：创建样本能完成，创建加删除样本失败；删除路径是需要追踪的边界。结合 shim 函数与 broker IPC 的观测，删除密集型测试可能受守卫影响，但尚不能把 full 门禁的全部延迟归因于删除，也不能由这两个样本推导所有读取、计算或 I/O 的开销。

**尚未定论**：`HTTP_PROXY` 对**联网测试**的额外延迟未实测。含网络调用的测试应单独怀疑。

### 3.1 ZCode 会话实测（2026-10-05，指纹面外）

ZCode 沙箱会话内（Bash 工具直跑 pwsh 子进程）：§2.1 全部环境变量为空、`(Get-Command Remove-Item).CommandType` 为 `Cmdlet`（未包装）、30 文件递归删除历史诊断样本 **0.01s**——当前指纹面内**无任何仪表化**，主工作树全量分片实测 211s（≈CI 水平）。该样本只作历史诊断记录，不是 full 门禁的前置测量。

- 小时级膨胀的实证（§1）来自**命中这些指纹的 WorkBuddy 系宿主会话**，不能外推到所有 AI 会话；无指纹会话的正常耗时也不证明其他宿主永远不会变慢。
- `run-local-quality-gates.ps1` 已按 §2 的 shim/environment 指纹（safe-delete 环境标记、sandbox IPC、Node/Python shim、`Remove-Item` Function 包装）阻断非 CI 的 `-Profile full`（`-AllowShimmedFull` 显式豁免）；普通代理、跨盘 Temp worktree 等未被证明属于同一原因的慢路径不在该阻断覆盖内，仍按 §4 报告条件与缺口。

### 3.2 WorkBuddy 沙箱内逐操作单价（2026-10-05 实测，指纹面内）

同一次会话内的进程内采样（探针见 `reports/agent-review/probe-sandbox-cost*.ps1`）。**结论：被代理的是「变更类」操作（删除条目、创建进程）；读取、枚举、哈希、脚本解析全部正常。**

| 操作 | 沙箱内实测 | 判别 |
| --- | --- | --- |
| `Remove-Item -Recurse` 10 / 50 / 200 / 1000 文件 | 0.72s / 1.84s / 6.04s / **27.99s**（≈28ms/文件，线性） | 按条目计费 |
| `Remove-Item -Recurse` **100 目录 × 3 文件** | **58.55s（≈0.5s/目录）** | 目录删除比文件删除贵 ~18× |
| 创建 200 文件 | 0.50s | 变更类，但远低于删除 |
| `git init + add + commit`（1 夹具仓） | **5.36s** | per-test git 夹具是重灾区 |
| 子进程创建（热态） | 0.99–1.19s | ~10× 原生 |
| 子进程创建（冷/争用） | **60.08s**（首个子进程） | 间歇、不可预测 |
| pwsh 进程创建 → 脚本第一行 | 1.84s（热）／**~228s**（冷，观测 1 次） | 0 字节日志的来源 |
| `Get-ChildItem -Recurse` 14585 文件 | 1.76s | **正常（1×）** |
| `ReadAllText` 1.6MB × 100 | 0.71s | **正常（1×）** |
| `Test-Path` × 500 / `Get-FileHash` 420KB | 0.13s / 0.00s | **正常（1×）** |
| `Get-Date` / 纯字符串字面量 | 0.06s / 0.00s | **正常（1×）** |

**间歇性（不可用单次耗时下结论）**：同一台机器、同一个文件，`tests/Unit/Log.Tests.ps1`（2 用例）本日先后为 **122.1s** 与 **7.7s**（13.6×）；同一 6 文件批（387 用例）在 16:36 为 **40.9s 全绿**。

**⚠️ 对 §3 表格的更正**：2026-10-04 记的「创建 40 文件 + 递归删除 → 第一轮即无输出、exit 1」**不是可复现的守卫行为**。2026-10-05 的 200 / 1000 文件与 100 目录样本**全部正常完成（exit 0）**，未被杀。那条记录的更可能解释是**工具调用超时或宿主侧瞬时停顿**，而非确定性的守卫终止。

> ⚠️ **2026-10-06 更正（覆盖本节旧注记）**：旧版本此处写「守卫（阈值 50）作用于 Git Bash 的 `rm` / `safe-bin` 包装，**不作用于 PowerShell 的 `Remove-Item`**」——**该结论已证伪**。实测在 PowerShell 会话里用 `Remove-Item -LiteralPath <dir> -Recurse -Force` 删除 `~/.workbuddy-ai/logs/<日期>` 时，守卫**确实**返回：
>
> - `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn"}` —— **单次（per turn）超过 50 个文件即要求宿主确认**；
> - `[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"reason":"trash-failed"}` —— 无回收站时的同一守卫。
>
> ⇒ 结论：**守卫位于删除通道而非 Git Bash 包装**，换 shell 绕不过。仍按规则 4：**不得拆小批或反复重跑来规避**，应把路径报给用户。

### 3.3 优化杠杆实测：哪些有用、哪些没用（2026-10-05）

**结论：主导成本是「删除的嵌套目录条目数」，不是外部进程启动次数、也不是删除调用次数。**

> ⚠️ **2026-10-05 更正**：早先版本把"减少外部进程启动次数"列为**唯一**有效杠杆，并据一次"35 个扁平文件逐条删除 vs 一次递归删除 = 24.7×"的样本推断"按 `Remove-Item` 调用计费"。后续更严格的对照**推翻了这个模型**：那次样本用的是**扁平文件**，与真实夹具的**嵌套目录**形态不可比。按目录条目重新采样后，删除成本与**调用次数几乎无关**（一次递归 vs 逐条相差仅 1.1×），而与**目录条目总数**强线性相关。

| 尝试 | 实测 | 判定 |
| --- | --- | --- |
| **删除 60 目录 × 1 文件：`Remove-Item -Recurse` vs `[IO.Directory]::Delete($p,$true)`** | **36.48s vs 36.04s** | ❌ **无差异**——拦截点在 .NET API **之下**，换实现绕不掉（推翻"native 可绕过包装"的旧假设） |
| 删除 60 目录 × 1 文件（≈0.61 s/目录） | 36.5s | 📌 目录删除单价 |
| 删除 35 个嵌套夹具目录（≈210 目录） | 128s（逐条）vs 118s（一次递归） | **1.1×**——调用次数**不是**成本因子 |
| 创建 100 目录 / 创建 100 文件 | 0.32s / 0.43s（≈3–4 ms/项） | ✅ 创建便宜 |
| 按目录/文件分离的删除缩放（见下表） | 目录线性、嵌套文件超线性 | 📌 见 §3.4 |
| `git init --template=`（空模板） | 条目 27→9，耗时 0.40→0.32s；完整夹具 4.27→4.40s | ❌ 无效——夹具成本由**产出目录数 + 进程启动**共同决定 |
| **一次 `git init` + 逐次复制 `.git`（旧写法）** | 0.36s → 0.05s / 仓 | ✅ 有效（但见下：仍留下 9 个目录/仓） |
| **`.git` 目录树 → 单行 `.git` 文件标记** | 夹具 60 → 42 目录（**-30%**） | ✅ **有效**（`Get-RuleEstateTargets` 同时接受 `.git` 目录或文件；已用于 `RuleEstate.Tests.ps1`） |
| **夹具仓预建一次 + 复制（`RuleEstateMutation`）** | 24 夹具 × 2 仓 × 5 git 进程 = **240 次进程启动 → 48 次** | ✅ 有效 |

> 推论：**夹具应最小化"产出目录数"**，因为沙箱按目录条目计费删除。`.git` 这类多目录产物能用**单文件标记**替代的就替代；确需真实仓时预建一次再复制，而不是每个夹具重跑 git。

### 3.4 删除成本的按条目缩放（2026-10-05 实测，含 1 次超线性观测）

对同一台机器、同一次会话的进程内采样（探针 `artifacts/work/ai-session-verify/probe-scale.ps1`）：

| 形态 | 目录 | 文件 | 实测删除 | s/目录 | s/文件 |
| --- | --- | --- | --- | --- | --- |
| 10 × (`d{n}/f1`) | 10 | 10 | 6.45s | 0.645 | 0.645 |
| 100 × (`d{n}/f1`) | 100 | 100 | 62.63s | **0.626** | 0.626 |
| 10 × (`d{n}/f1..f20`) | 10 | 200 | 16.14s | 1.614 | 0.081 |
| 100 × (`d{n}/f1..f20`) | 100 | 2000 | **488.84s** | **4.889** | 0.244 |

- 前两行证明：**目录数 10→100 时耗时严格线性（≈0.63 s/目录）**，与文件数、调用次数无关。
- 后两行显示**超线性**：同一目录数下堆入更多文件会进一步放大（100 目录从 0.63 → 4.89 s/目录，**7.8×**），说明沙箱对"深目录 + 多文件"的复合形态另有一层开销（本会话内 1 次观测，不排除宿主瞬时停顿；但方向与 §3.2 的"目录比文件贵"一致）。
- **可复用的保守预算：≈0.15–0.63 s/目录**（本次真实夹具 5 个 = 44.73s ≈ 0.149 s/目录；纯合成样本 ≈0.63 s/目录）。用**目录数**估算夹具删除成本，比用"调用次数"或"文件数"都可靠。

### 3.5 修正后的实测单（覆盖 §3.2）

§3.2 的"`Remove-Item -Recurse` 按**条目**线性 28ms/文件"**对文件成立、对目录严重低估**。修正：

| 操作 | 沙箱内实测 | 判别 |
| --- | --- | --- |
| 删除扁平**文件** N 个 | ≈28ms/文件（线性） | 按文件条目计费 |
| 删除**嵌套目录** N 个 | **≈150–630ms/目录** | 按目录条目计费，**比文件贵 ~5–22×** |
| 创建条目（文件或目录） | ≈3–4ms/项 | 便宜 |
| `git init` 单次 | 0.36–0.40s | 进程启动计费 |
| 子进程创建（冷/争用） | 最高 60.08s（长子进程）；pwsh 首行最高 ~228s | 间歇、不可预测 |
| `Get-ChildItem -Recurse`、`ReadAllText`、`Test-Path`、哈希 | ≈1× 正常 | 读取类不计费 |

> ⚠️ 一次会话的样本不构成普适常数；跨宿主复用前必须重新探测（§6）。

### 3.6 未被 §3 覆盖的成本面：只读 open 的规则决策量（2026-10-06 实测）

§3.2–§3.5 测的是**变更类**操作（删除、创建、进程启动）。本轮补充一个此前未记录的面向：**沙箱中心对每一次文件访问都记一条 `decide_file` 决策日志**，而这条路径是**串行 + 同步落盘**的。

| 观测 | 实测值 |
| --- | --- |
| 今日 `decide_file query_only=true` | **261,071 次** |
| 今日 `cmd_modify_backup` | 28,274 次 |
| 今日沙箱日志总量 | **~2.5 GB / 247 个文件**（10 MB 轮转）；`logs/sandbox` 累计 4.37 GB |
| 日志行间隔实测（连续 38 行） | 118 ms ⇒ **~3.1 ms/次**，即决策路径 **~320 次/秒** |

**能确认的**：决策路径有可观测的速率上限量级（~320 次/秒），且**决策量本身会变成磁盘负担**（2.5 GB/天）。当上层组件对一个 10 万文件级的目录树逐文件发起访问时（本轮实测：`workspace/sessions/**` = **88,099 文件**、`%TEMP%` = **114,255 文件**），这条路径就是量级放大的来源。

**不能确认的**（不要外推）：

- 3.1 ms/次**是到达率还是吞吐上限，日志无法区分**。若为上限，则 10⁵ 次 open ≈ 5 分钟；若上层本身并发度不足，则耗时另算。
- §3.2/§3.5 的 `Get-ChildItem -Recurse` 14585 文件 = 1.76 s（≈1×）说明**纯枚举不计费**。本轮观测到的 3.1 ms/次出现在**并发多线程逐文件访问**的场景，与单线程枚举不可直接比较。
- 未做端到端 A/B 计时（切换动作前后秒表对照），因此"某功能变慢"只能标为**强证据推测**，不能标为实测。

**上报上游的期望修复方向**：只读（`query_only=true`）的规则决策**不应逐次同步写日志**（应采样/异步/按会话聚合），且不应成为吞吐瓶颈；决策日志应有总量上限。

## 4. 操作规则（防重现）

1. **耗时结论必须限定执行环境。**
   对"门禁要 5 小时 / 测试太慢"的判断，应保持源码、测试选择、并行度与依赖可比，并在已授权的用户终端或 CI 对照复核。CI 超时预算以 `.github/workflows/ci.yml` 为准；预算配置不是实际运行耗时或成功证明。
2. **按风险选择验证，再选择可完成该验证的执行位置。**
   agent 内默认沿 auto/focused 完成最低充分证明；仓库风险确需 full 时，仍须获得一次有效 full 结果。守卫阻断或执行环境不可用时，记录缺口并使用已授权的 CI/终端路径，不把抽样升级成 full 通过，不因环境受阻修改安全控制。
3. **报告耗时必须带条件。**
   写明"经 agent 工具启动 / 命中 shim 指纹"，否则读者会默认它是代码成本。
4. **夹具最小化「产出目录数」，其次才是进程启动次数。**
   删除是**按目录条目计费**的沙箱开销（§3.4：**≈0.15–0.63 s/目录**，嵌套深且文件多时更高；扁平文件约 28ms/文件），是本类"测试很慢"的**首要**来源。夹具优先**扁平、少量目录、少量文件**，避免多层嵌套目录树。
   - `.git` 这类多目录产物：若调用方只做**存在性判断**，改用**单行 `.git` 文件标记**（`Get-RuleEstateTargets` 同时接受 `.git` 目录或文件）⇒ 一个仓少 9 个目录。
   - 确需真实仓时：**预建一次**（含 commit）再 `Copy-Item -Recurse`，不要每个夹具重跑 `git init` + `add` + `commit`（§3.3：5 次进程启动/仓）。
   - ⚠️ 不要指望换删除实现（`[IO.Directory]::Delete` 与 `Remove-Item` **同价**，§3.3）——拦截点在 .NET 之下。
   Git Bash 的 `rm` / `safe-bin` 包装在批量删除时还会触发守卫（阈值 50）并要求**宿主弹窗确认**——agent **不能自我批准**。
   ⚠️ **不得**以"拆小批删除 / 删失败就静默放弃"来规避守卫——那属于绕过安全控制。
5. **不要从 agent 内关闭或绕过 shim / 代理。** 需要干净环境时，换执行位置，而不是改安全配置。
6. **不要把测试输出静默重定向到文件后干等。**
   完成前日志是 **0 字节**（§3.2），叠加间歇的进程创建停顿后，"仍在启动"与"已挂死"在观感上无法区分。用后台任务 + 事后读日志，并在判定挂死前先确认**进程是否还活着**与**是否有回执**（`reports/test-shards/**/targeted.receipt.json`）。
7. **夹具复用优先于反复调用外部命令。**
   每个 git / CLI 调用都按"进程启动"计费（§3.3：`git init` 0.36s/次 vs 复制现成仓 0.05s/次）。per-test 的 `git init` / `git config` / CLI 调用是测试变慢的**次要**可控项（首要项是目录数，见规则 4）；能用一次准备 + 复制/复用替代的，就不要每次重跑。**但要连带检查复用的产物本身含多少目录**——复制一个 9 目录的 `.git` 只省了进程启动，删除时仍要按目录付费。

## 5. 上报上游所需的复现材料

若要让**产品侧**彻底修复（而不是每次靠人识别），带上以下最小证据：

1. 指纹：`env` 中 `CODEBUDDY_SAFE_DELETE_*`、`NODE_OPTIONS`、`PYTHONPATH`、`HTTP_PROXY` 的**存在性**（值可脱敏）。
2. `(Get-Command Remove-Item).CommandType` 的输出。
3. 对比数据（**按目录条目，不是按调用次数**）：
   - 纯创建：100 目录 0.32s；100 文件 0.43s。
   - 删除**嵌套目录**：10 目录 6.45s；100 目录 62.63s（**≈0.63 s/目录，线性**）；真实夹具 5 个 ×60 目录 = 44.73s（≈0.15 s/目录）。
   - 删除**扁平文件**：≈28ms/文件（线性）。
   - **删除实现对照**：60 目录 × 1 文件，`Remove-Item -Recurse` 36.48s vs `[IO.Directory]::Delete($p,$true)` 36.04s（**无差异**）。
   - **调用次数对照**：35 个嵌套夹具目录，逐条删除 128s vs 一次递归 118s（**1.1×**）。
   - 复合形态（100 目录 × 20 文件 = 2000 文件）：488.84s（≈4.89 s/目录，**超线性**）。
4. 期望的修复方向：删除拦截应**按操作成本而非按目录节点计费**；**目录删除不应比文件删除贵 5–22×**；或提供**文档化的干净测量模式**（`[IO.Directory]::Delete` 已证明绕不过拦截，说明拦截在 .NET 之下，需要产品层提供通道）。

## 6. 边界

- 本文是**本机 2026-10-04 / 2026-10-05 的实测**，指纹与阈值随客户端版本可能变化；复用前重新探测。
