# Model Presets

This independent PowerShell 7 tool projects the joint model pool defined in `presets.json` (schema v7). It does not select gateways, inspect credentials, retry tasks or run background monitors.

The ChatGPT Desktop/Codex orchestration pool exposes three model families and three exact tuples: GPT-6 Luna at `max`, GLM-5.3-Flash at `xhigh`, and Gemini 3.8 Flash at `high` (Codex catalog slug `gemini-3.8-flash-high`). All three tuples are projected as native Codex agent roles after the current `codex debug models` preflight; named task slots pin their exact model and effort. The user has also confirmed successful prior ChatGPT Desktop use of GLM, Haiku and Gemini. An earlier task-payload probe failed for three children, but that does not negate model availability or the user's live evidence and is no longer used to gate native role projection. The task routes use Gemini high for quick triage, standard review and deep implementation, GLM xhigh for routine maintenance, bounded implementation and test execution, and Luna max for deep investigation, documentation review and architecture review. These defaults come from a real-API evaluation (2026-10-18, allowlisted tuples only), not from vendor positioning alone. Other hosts stay within their own native model families: ZCode uses only GLM/max, and Antigravity remains on its `inherit`/`flash`/`pro` tiers because it cannot express these exact model/effort tuples. No Codex model or effort is projected to those hosts. The Claude family (Haiku) was retired from the pool by user decision on 2026-10-20; DeepSeek and Terra are removed. Each child task may use an exact supported tuple from its host pool, and different tasks may use different models. `default_preset=gpt6_luna_only` remains the default parent preset; it does not disable automatic subagent routing across all three families. `-SubagentsOnly` preserves the parent model and review selection when projecting subagents. Menu order is per-model effort, not a cross-model performance ranking.

The executable enforces a closed, host-specific tuple allowlist, so adding a preset or changing `presets.json` cannot expand it: Codex allows `gpt-6-luna/max`, `glm-5.3-flash/xhigh` and the native Gemini catalog ID `gemini-3.8-flash-high/high`; ZCode allows only `glm-5.3-flash/max`. The retired `claude-haiku-5-5` tuples are rejected everywhere. The native Codex catalog uses `gemini-3.8-flash-high` as the model ID for Gemini 3.8 Flash at high effort; the bare product-family string `gemini-3.8-flash` is not an accepted alias.

Menus must contain one model in strictly increasing effort order. Resolve rejects reversed or mixed-model menus. Every active model now has exactly one allowed effort per host, so task complexity changes a task's slot or supported model, not its effort. The ZCode GLM facet stays at max. Failure output may describe lower/higher menu entries, but never instructs the caller to exhaust those entries before selecting another model.

An ordinary host AI can classify a task, split its dependencies and choose the deterministic slot route before dispatch. Delegate only when the user or applicable instructions explicitly authorize delegation. Parallel dispatch additionally needs independently verifiable slices, disjoint write sets, positive benefit and the host's native concurrency budget. These presets provide a deterministic slot route; they do not install a background scheduler or grant delegation permission.

- Choose `quick_triage` for a small read-only lookup, known error classification or concrete evidence check.
- Choose `routine_maintenance` for a small, well-understood fix; `bounded_implementation` for a specified change with explicit write set and proof; `standard_review` for read-only review; and `test_execution` for a scoped test command and failure diagnosis. `documentation_review` checks written contracts and `architecture_review` checks interacting constraints or security boundaries.
- Choose `deep_investigation` for unresolved cross-module behavior, root cause, architecture or security questions. It is read-only and returns evidence plus a proposed bounded change. Use `deep_implementation` for the resulting complex change only after scope and write set are explicit.
- Choose the model independently by task fit: vendor descriptions position Luna for efficient focused work, Gemini Flash for long-horizon software engineering and autonomous agents, and GLM for coding. These statements do not establish a shared ranking, actual latency, cost on the selected endpoint or task accuracy. The Codex route table uses the exact supported tuples below; ZCode narrows to GLM/max. Antigravity's tier-only menu cannot express these exact tuples. If a child returns unresolved uncertainty, the parent reviews its evidence and remaining scope before re-selection; completed writes are not replayed.
- Return to a smaller scope for the next independent task once the remaining question is concrete. Every active model is single-tier. Choose the model independently by task fit and current support; there is no measured universal ranking between these models.
- Missing input requires clarification. Authentication, provider, tool and 429 failures require their own diagnosis; they do not justify increasing effort or blindly repeating a task.

When a tuple is unavailable, the parent may choose another supported pool tuple for the remaining or next bounded task and record the reason. Whole-preset switching is not required. Preserve scope, proof and prior work; do not replay completed writes or silently substitute effort. A runtime failure is not itself evidence that another model is entitled or that higher effort will fix it.

Each slot lists at most three exact alternates with `preset`, `model` and `effort`; an empty list means no alternate. The launcher has two capability modes. In `native` mode it preflights `codex debug models` and requires the exact model slug and reasoning level to be present. `AvailablePreset` and offline Resolve describe routes, not entitlements; a model entry alone does not establish support for every configured effort. In `provider_override` mode it requires a current, unexpired receipt with a verified exact tuple plus `provider_id`, `surface`, `observed_at`, `expires_at` and `source`; the provider ID must match the selected profile/base configuration. Both execution modes require a declared custom provider and per-invocation retry caps. A static MOR-090 row alone is not current temporal evidence. The launcher does not retry or upgrade the tuple. Retain unsupported tuples as configuration only. Do not infer aliases from display names or silently replace a selected effort. Catalog observations and provider receipts do not establish a successful request.

Native catalog snapshots passed through `CapabilityProbePath` must include the usual `models` array plus `source: "codex debug models"`, the absolute target `codex_root`, and `observed_at` / `expires_at` timestamps. The window must be current, not future-dated, and at most five minutes long. Raw or stale catalog files fail closed. Live projection probes launch with the requested `CodexRoot` as the child's `CODEX_HOME`, so another configuration root cannot silently supply capability evidence. Provider-override receipts keep their separate provider-bound contract.

The controlled launcher bounds execution with `-TimeoutSeconds` (default 900, range 1–3600) and catalog lookup with `-ProbeTimeoutSeconds` (default 30, range 1–120). Process waits and redirected-output reads are both bounded. A launch timeout terminates the launched process tree where possible and reports `launcher_timeout` / `diagnose_before_any_new_dispatch`; it never retries. A CLI process stopping does not prove the upstream request was cancelled or that partial writes were rolled back: inspect the worktree and existing task result before deciding whether any remaining work can be dispatched. Projection's live catalog probe has a fixed 30-second process deadline and bounded output reads.

Failure classification consumes structured JSON error fields (`code`, `reason_code`, `category`, `type`, `status` or `http_status`) only. It examines the complete output stream with precedence account risk > auth/permission > rate limit/quota > tool/environment > overload, so an early 503 cannot hide a later stop condition. Free text, including a model message that merely mentions `timeout`, remains `unknown` and stops for diagnosis; the launcher never guesses an upstream outage from prompt or log text.

Honor upstream `Retry-After` and quota reset before considering another dispatch. Do not clear cooldowns, rotate identities, or switch models to evade a restriction. OpenAI's [rate-limit guide](https://developers.openai.com/api/docs/guides/rate-limits) notes that limits include both requests and tokens and that unsuccessful requests also consume limits. Higher effort can increase latency and token use; repeated requests are not evidence that a model has become less capable. Zero launcher retries reduces amplification but does not establish account safety or control a native host, SDK, or relay's retries.
