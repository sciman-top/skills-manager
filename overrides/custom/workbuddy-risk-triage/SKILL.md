# WorkBuddy 风控分诊

## 核心认知：三类报错是同一个根因

`11140` / `403 request illegal` / `未知错误暂无响应` **不是三个问题**，而是**服务端账号级风控拦截**的三种外壳。请求**在到达模型之前**就被丢弃。

因此以下操作**全部无效**（不要浪费时间，更不要反复做）：

| 无效操作 | 原因 |
|---|---|
| 重装客户端 | 故障点不在本地 |
| 清缓存 / 删 AppData | 风控状态在服务端 |
| 退出账号重新登录 | 账号身份没变 |
| 换自定义模型 / 第三方 API | 请求到不了模型层 |
| 反复重试 / 反复重启 | **有害**，会被判为异常行为，让风控收紧 |

**唯一有效的本地判据**：换一个账号能正常 → 确认是账号级；换手机热点能正常 → 是 IP 级。

`403` 括号内 `(32位hex/UUID)`：hex 是请求/链路 ID，**UUID 是会话（任务）ID**，可在
`~/.workbuddy-ai/<uid>/sidebar-list-snapshot.json` 中比对确认归属。

**判据一句话：看 `category`，不看 `displayMsg`。** 真实响应体里 `"category":"internal"` +
`statusCode:403` + `code:11140`，那句「内容未通过安全审核」是**通用包装文案**。
若连只发「你好」的会话也是 `state=error`，内容变量即被排除 → **只能是账号级**。
（读取方法见 `references/log-forensics.md`）

## 分诊步骤（按顺序）

### 1. 先跑自检脚本，拿到环境基线

```
bash "<风控工具目录>/workbuddy-risk-selfcheck.sh"
```

> `<风控工具目录>` = 本仓 `docs/handover/ai-risk-control/tools/workbuddy/`；部署落位与资产清单见同目录 `ASSETS.md`。

只读，覆盖 9 项：hosts 劫持、自定义模型/反代进程、客户端第三方指向、多账号共用设备指纹、
代理例外规则、**代理例外覆盖缺口（WinINET vs 环境变量）**、重启频率、
**实际服务错误日志（403/11140/429）**、**活动自动化与 MCP 认证重试**。**有高危项返回 1**。

> ⚠️ **第 8 项与第 9 项各有陷阱，都已修掉：**
>
> - **第 9 项「MCP 认证失败」四重陷阱**（数行数 / 扫全部日志 / 内置插件 / 全局计重试），
>   另加「官方网关连接器」一类。**误判会造成"永久狼来了"，把真实高危淹没。**
> - **第 8 项「实际服务错误日志」的自污染**：扫描面必须限定在 `*/sdk/conversations/*.log`。
>   会话日志记录了你执行过的命令与写过的文档 —— 只要文本里有 `429 Too Many Requests`，
>   就会被当成真实命中（实测：写一份含该串的报告后计数从 14 涨到 27，全是假的）。
>   **计数在你写文档/跑命令之后突然上涨 → 先怀疑自污染，不要怀疑账号。**
>
> 完整拆解见 `references/selfcheck-internals.md`。

### 2. 按结果对号入座

| 自检结果 | 指向 | 处置 |
|---|---|---|
| hosts 含 workbuddy/codebuddy 条目 | 灰产「积分充值」劫持 | 高危，官方明确封号，清除并排查来源 |
| `models.json` 非空 | 接了反代 / 中转站 | 高危，官方「一经发现做封号处理」 |
| 发现 workbuddy2api / workbuddy-proxy / flowrebound 进程 | Token 被提取对外供 API | 高危，立即停用并轮换凭据 |
| `settings.json` 含 baseUrl/apiKey/endpoint | 客户端指向第三方 | 核对是否非官方服务 |
| 账号数 > 1 | 同设备多账号 | 有连坐风险，不要再切换/新注册 |
| 代理例外缺 workbuddy.ai | 流量走代理出口 IP | 补 `*.workbuddy.ai`（国际版）/ `*.workbuddy.cn`（国内版） |
| 今日启动 > 8 次 | 反复重启 | 停手，不要靠重启试 |

### 3. 确认客户端是国际版还是国内版（**关键前置**）

```
grep -o -h -E 'https?://[a-zA-Z0-9._-]+' ~/.workbuddy/logs/*/[a-z]*.log \
  | sed 's#https\?://##' | sort | uniq -c | sort -rn | head
```

- `www.workbuddy.ai` → **国际版**（解析到腾讯云海外节点）
- `www.workbuddy.cn` → 国内版

**必须先确认这个再判断代理规则对不对。** 曾因假设是 `.cn` 而误判用户规则「后缀写错」，实际是 `.ai` 且完全正确。

### 4. 归因失败信号（live 阶段用）

| 现象 | 指向 |
|---|---|
| 新账号也开始报 11140/403 | **设备/IP 维度**，换账号这个解法本身无效 |
| 只有特定话题触发 | **内容安全**路径 |
| 只有特定时段触发 / 429 | **限流/调度**路径 |

## 429 与 403 是两件事（**不要混判**）

403/11140 是**未公开细则的账号级风控**；429 是**官方承认的频率/额度限流**，服务端会给出准确恢复时刻。
实测错误体（换号之后的新账号）：

```
{"code":-32003,"message":"Quota exceeded: 429 usage exceeds frequency limit,
 but don't worry, your usage will reset at 2026-09-30 21:49:20 UTC+8,
 alternatively, you can switch to the other models to continue using it.
 (32位hex/会话UUID)", "data":{"statusCode":429,...}}
```

- **格式与 403 相同**：`(hex/UUID)`，UUID 仍是**会话 ID**，不是账号令牌。
- **reset 时间不止一个尺度**：实测同一天出现过 `05:56` 与 `21:49`（UTC+8）两个 reset 点
  → 限流窗口有**长周期额度**与**短周期频率**两种。
- 官方把 `6003 / 6004` 定义为「请求频率受限，**专业版也会出现**」，建议「**优先切换模型重试**」；
  429 属同族机制 —— 切模型是**官方认可**的分流手段。
- **处置完全不同**：403 靠换号/申诉/等待；429 靠**等 reset + 切模型 + 把长任务切段**。

## 换号只能止血，不能根治（**最容易漏判的一点**）

**换账号解决的是「这个账号被标记了」，解决不了「这套用法会被标记」。**

实测对照：旧账号被风控后换新号，新号 403/11140 **归零**（证明是账号级），
但新号的会话主题分布与旧号**同源** —— 旧号是「fq 网关客户端 key / CLIProxyAPI / CPA 网关 / OAuth」，
新号仍是「审查 Direct OAuth 与 CPA 网关 / 升级 CLIProxyAPI / 修改 CPA 路由 / 排查 CLIProxyAPI 网关」。
**行为画像原样搬了过去，复发只是时间问题。**

所以判「是否已彻底修复」必须分两层：

| 层 | 判据 |
|---|---|
| 止血 | 换号后 403/11140 归零、环境项全绿 |
| 根治 | **新增会话是否已脱离触发画像那一簇** —— 没脱离就是没根治 |

配套动作：**把反代 / 网关 / 密钥 / 绕过类工作彻底移出 WorkBuddy 会话**，放到本地终端或其它工具里做。

## 降智（变笨）的三类归因

不要把「降智」当成单一现象：

1. **上下文型**（最常见）— 长对话信息堆积、规则冲突、模糊词漂移。
   解法：开新会话；蒸馏记忆文件（>30 天未引用压成一行）；给冲突规则加优先级/适用条件。
2. **调度型** — 高峰期算力紧张被分配到轻量模型/节点。
   解法：重任务避高峰；固定模型版本，不要来回横跳。
3. **风控型** — 被软限流降优先级。
   **无官方承认、缺硬证据**。可确证的惩罚是显式的 11140/403/429，不是静默降智。
   解法：按上面的分诊流程走，不要靠换模型硬扛。

**顺序：先怀疑自己的上下文，再怀疑调度，最后才考虑风控。**

## 红线（碰了就从"临时限制"升级为"永久封禁"）

**条款号必须先确认是哪一份协议** —— 存在两份并行的协议，编号完全不同，混引会翻车：

| 协议 | 条款号 | 备注 |
|---|---|---|
| **WorkBuddy 国际版**（`www.workbuddy.ai/document/term`） | **6.4 / 5.2 / 3.5 / 6.3 / 12.1 / 12.2** | `.cn` 站同页也是**英文版**；16.6 条明确**英文版优先效力** |
| **CodeBuddy / 腾讯云代码助手系**（中文协议） | **8.1.3 / 9.1 / 9.2** | 与 WorkBuddy 账号体系互通（8.1.3），一侧违规影响另一侧 |

→ **引用时说明是哪一份**，或者干脆**只引条款内容不引编号**。条款原文与官方定性见 `references/official-sources.md`。

**禁止的核心内容**（国际版 6.4(a)(d)(f)(j) / 5.2(a) / 3.5）：
反编译反汇编、自动化提取数据、**抓取客户端与服务器之间的传输（= 抓 Token）**、**绕过限制或保护措施**。
协议 **3.5** 明确服务**内置检测「规避手段 / 未授权及恶意程序」**，检测到会回传账号 + 用户 ID + 程序信息。

> ⚠️ **12.2 的「违规次数」是关键** —— 反复触发会把**可恢复的轻度限制升级为不可恢复的封禁**。
> 这也是「报错后反复重试」有害的协议依据。

**因此不要做**：伪造 `device-id` 摆脱账号关联、篡改客户端状态、改 hosts 接中转站、
买第三方「低价积分/源头充值」、账号出租出借转卖、批量注册、**报错后反复重试/重启**。

这些不但没用（服务端已有映射），还会把可恢复的轻度风控变成不可恢复的封禁。

## 必须警惕的两类信息污染

### ① 「429 限流解决方案」软文 → 实为封号加速器（**危害最大**）

搜「WorkBuddy 429 限流」会大量命中一批**看似技术实测、实为推广软文**的文章
（掘金 / 知乎 / CSDN / 博客园，内容高度雷同，常带「本文含工具实测分享」字样），
推销一个叫 **FlowRebound「大模型稳流器」** 的本地工具。核心操作步骤是：

> 「去到 WorkBuddy / Trae 的**自定义模型设置页面，把接口地址换成工具给出的本地地址**」

**这一步就是「绕过限制措施 / 规避技术措施」。**
它把请求改道经过一个第三方本地代理 —— 正是官方明确「一经发现做封号处理」的形态
（与「低价积分」灰产同一套手法：篡改本地配置接入外部模型）。
文章里「不会破解、绕过、突破官方限流策略」的自我声明与操作步骤自相矛盾。
同批文章还把「自建中转网关」列为对比方案 —— 同样在红线上。

自检脚本已把 `flowrebound` / `workbuddy2api` / `workbuddy-proxy` 列入**反代类进程**检测项。
**看到就划走。**

### ② 编造的后台与接口

网上大量「WorkBuddy 敏感词拦截解决办法」是 **AI 批量生成的虚假内容**，特征：

- 编造不存在的后台菜单（如「安全与合规 → 内容审核设置」）——WorkBuddy 是桌面客户端，**没有这个后台**
- 编造不存在的 API 端点（如 `/v1/generate/raw`）
- 方案本质是**教你绕过内容审核**

**看到就划走。** 照做正好踩中协议 6.4。

```
repo_verified -> filesystem_projected -> host_loaded -> live_accepted
```

- 判据：连续 3–7 天无 11140/403/429、长会话不断流、每日自检稳定高危 0

## 报错处置 SOP

**第 0 步：截图留证 + 立即停止重试。** 反复重试是唯一会让情况变坏的本地动作。

| 报错 | 先判断 | 处置 |
|---|---|---|
| 403 / 11140 | 账号级还是设备级？ | ① 手机热点测一次；② 换号测一次；③ **提交 Trace ID 工单**；④ 停 2–4 小时再试；⑤ 本地不做重装/清缓存/换 API |
| 429 / Quota exceeded | 读 reset 时间 | 等到 reset 再继续；期间按官方建议切模型；长任务切段 |
| 未知错误暂无响应 | 查真实响应体 | 读 `*/sdk/conversations/*.log` 的 `statusCode`/`category`，按上面两类归位 |
| 6003 / 6004 | 官方：频率受限 | 官方建议「优先切换模型重试」 |
| 3002 / 3003 / 3007 | 官方：网络环境 | 确认网络类型，**参照「网络代理」关闭网络代理** |
| 1001 / 11133 / 11134 / 14003 | 官方：模型侧状态 | 新开会话或切换模型 |
| 11115 | 官方：输入过长 | 精简输入或换大上下文模型 |

## 姊妹技能：Google 侧（Antigravity / Gemini）

同一套「反代 + 多账号 + OAuth 复用」的行为模式会**同时**触发 WorkBuddy 与 Google 的风控。
如果你的问题涉及 **Antigravity / Gemini**（封号、429、降智），加载
**`antigravity-gemini-risk-triage`** 技能。

**跨平台实证**：本技能记录的用户触发画像含 **CLIProxyAPI / CPA 网关**，而 CLIProxyAPI
正是 2026-02 与 2026-08 两轮 **Antigravity 封号潮**中被点名最多的工具
（其 GitHub Issue `#1637`：有人一次被封 3 个 Google 账号，另一人 40 个账号全灭）。
→ **在 WorkBuddy 换号躲过的用法，会在 Google 侧以更硬的方式再收一次账**
（真金白银的订阅 + Google 侧的二振永久封）。

## 主动防范：出事之前怎么做

> 以上各节是「出事之后」的分诊与处置。若目标是**防患于未然**，直接读 `references/prevention-ops.md`。

核心防范逻辑三句话：
1. **账号画像** 比单次行为重要——每天的会话主题决定中长期风险；换号只是止血，画像原样搬过去复发只是时间问题。
2. **停止重试** 比重启更重要——协议明确反复触发会把可恢复限制升级为不可恢复封禁。
3. **自检先于判断** ——出事后先跑自检脚本拿到环境基线，再对号入座，避免把自污染误判为账号风控。
